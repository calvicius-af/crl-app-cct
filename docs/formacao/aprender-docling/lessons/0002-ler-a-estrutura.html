1. Uma pequena convenção, vista de duas maneiras

Esquece "campos" e "DoclingDocument" por um bocado. Olha só para este pedacinho de uma convenção — é o mesmo tipo de excerto que viste na lição 1:

1.1 — Cada linha leva um post-it colado

Quando o Docling lê uma página, não te devolve só o texto: cola um post-it a cada bloco, a dizer o que aquele bloco é. Esse post-it chama-se rótulo (label, em inglês, dentro do código). Cinco exemplos, tirados de uma convenção:

CAPÍTULO I
→ cabeçalho de secção
Cláusula 1.ª — Âmbito
→ cabeçalho de secção
1 — O presente contrato coletivo obriga as empresas filiadas na associação outorgante…
→ texto normal
[Tabela: Remunerações mínimas — Nível, Categoria, €]
→ tabela
BTE 2 | 2025
→ rodapé de página

É só isto, para já: um pedaço de texto, e uma etiqueta a dizer o papel dele. No código, "consultar o post-it de um bloco" é escrever item.label — e o valor que lá vem é sempre um destes quatro que acabaste de ver (há mais do que quatro no total, mas nas convenções são estes que aparecem sempre).

1.2 — Duas maneiras de perguntar "o que há aqui dentro?"

Sabendo o post-it de cada bloco, o Docling ainda te deixa perguntar pela informação de duas maneiras diferentes — como fazes no teu Mac quando procuras um ficheiro: podes abrir pastas até o encontrares, ou podes pesquisar no Spotlight e ele aparece-te logo, sem te dizer em que pasta estava. É a mesma informação, duas formas de lá chegar.

Primeira maneira — abrir pastas. O documento vem organizado em pastas dentro de pastas: um capítulo contém cláusulas, uma cláusula contém os seus números. No código chamam-se body (o corpo principal) e groups; o rodapé fica fora do corpo, numa pasta à parte chamada furniture ("mobiliário" — o que não é conteúdo do contrato em si):

📁 Corpo do documento

📁 CAPÍTULO I cabeçalho de secção

📁 Cláusula 1.ª — Âmbito cabeçalho de secção

📄 "1 — O presente contrato coletivo obriga…" texto
📊 Tabela: Remunerações mínimas tabela

📁 Mobiliário fora do corpo

📄 "BTE 2 | 2025" rodapé

Esta vista responde a "o que está dentro do quê, e por que ordem se lê?". É o que o teu cct/extractor.py hoje reconstrói à custa de regex — capítulo contém cláusula, cláusula contém número.

Segunda maneira — pesquisar tudo de uma vez. O mesmo conteúdo, sem pastas nenhumas: uma lista única com tudo o que existe no documento, na ordem em que o Docling o encontrou — não necessariamente a ordem de leitura. No código chamam-se doc.texts, doc.tables, doc.pictures:

🔍 pesquisar tudo — doc.texts + doc.tables
"CAPÍTULO I"secção
"Cláusula 1.ª — Âmbito"secção
"1 — O presente contrato coletivo…"texto
Tabela: Remunerações mínimastabela
"BTE 2 | 2025"rodapé
O ponto principal desta lição

Repara: são os mesmos cinco blocos nas duas vistas. Não há dois documentos — há duas perguntas diferentes ao mesmo documento. "Pastas" dá-te a organização; "pesquisar tudo" dá-te o inventário total, sem organização nenhuma. É por isto que o código da próxima secção usa doc.iterate_items() em vez de percorrer doc.texts directamente: iterate_items() anda pelas pastas, na ordem de leitura — é a pergunta certa quando queres uma lista de cláusulas por ordem.

1.3 — A morada de cada bloco

Além do post-it, cada bloco de texto sabe de onde veio — a sua proveniência (prov, no código). Pensa nisto como uma morada postal com três linhas, cada vez mais precisa:

página
page_no — em que página do PDF está
posição
bbox — onde exactamente nessa página (uma caixa com coordenadas)
caracteres
charspan — a que posição do texto corrido isto corresponde

Este último é o que te interessa a ti: o teu doc.json vive de char_start e char_end, e é por aqui que a rastreabilidade sobreviveria a uma eventual troca de extrator. Confirma empiricamente a que texto é que esse intervalo se refere antes de construir alguma coisa em cima dele — é a experiência número um da tua lista.

Antes de avançar: queres a lista de cláusulas de uma convenção, por ordem, uma dentro da outra. Qual das duas maneiras usas?

2. O código

Já viste os três conceitos que o código vai usar: post-it (label), pastas percorridas por ordem (iterate_items()) e morada (prov). O script completo está em exemplos/listar_clausulas.py. O coração são estas linhas:

from docling.datamodel.base_models import InputFormat
from docling.datamodel.pipeline_options import PdfPipelineOptions
from docling.document_converter import DocumentConverter, PdfFormatOption
from docling_core.types.doc import DocItemLabel

opcoes = PdfPipelineOptions(do_ocr=False, do_table_structure=True)
conversor = DocumentConverter(
    format_options={InputFormat.PDF: PdfFormatOption(pipeline_options=opcoes)}
)
doc = conversor.convert("convencao.pdf").document

# a ordem de leitura é a ordem em que iterate_items devolve os itens
for item, nivel in doc.iterate_items():
    if getattr(item, "label", None) is DocItemLabel.SECTION_HEADER:
        pagina = item.prov[0].page_no if item.prov else "?"
        print(f"p.{pagina}  {'  ' * nivel}§ {item.text}")

Linha a linha, em português — não precisas de saber Python para seguir isto:

LinhaO que faz, por palavras
opcoes = PdfPipelineOptions(…)Prepara as instruções de leitura: sem OCR, com reconhecimento de tabelas — como as flags da lição 1, mas escritas em Python em vez de na linha de comandos.
doc = conversor.convert(…).documentConverte o PDF. doc é a partir daqui "a convenção lida", com as duas vistas da secção 1 já disponíveis lá dentro.
for item, nivel in doc.iterate_items():"Abre as pastas", uma de cada vez, por ordem de leitura. Cada volta do ciclo dá-te um bloco (item) e a profundidade a que está aninhado (nivel — 0 é o topo, 1 é uma pasta dentro dele, etc.).
if getattr(item, "label", None) is DocItemLabel.SECTION_HEADER:"Olha o post-it deste bloco — só me interessa se disser 'cabeçalho de secção'." É o filtro que separa CAPÍTULO I/Cláusula 1.ª do resto.
pagina = item.prov[0].page_noLê a primeira linha da morada do bloco — a página do PDF onde está.
print(f"p.{pagina} …")Escreve a página e o título, com espaços a mostrar a profundidade — o mesmo efeito visual das pastas aninhadas de cima, mas em texto.
Guarda só para quando precisares — a armadilha da configuração

Isto não é para perceberes agora, é para reconheceres se um dia aparecer: se copiares o código com {"pdf": PdfPipelineOptions(...)} em vez do que está em cima, o Python não avisa logo — só se queixa mais tarde, com AttributeError: 'PdfPipelineOptions' object has no attribute 'backend'. Se vires esse erro, é isto: falta a camada PdfFormatOption à volta.

Os valores por omissão, verificados

Estes são os valores de PdfPipelineOptions() na versão 2.121.0, lidos do pacote instalado — não são o que a documentação diz, são o que o código faz:

3. As tabelas, que é onde está o dinheiro

Literalmente. As tabelas salariais são o conteúdo que o teu extractor hoje trata pior — delimita-as com sentinelas e devolve-as como texto. Aqui saem estruturadas:

for tabela in doc.tables:
    df = tabela.export_to_dataframe(doc=doc)   # pandas.DataFrame
    print(tabela.data.num_rows, "x", tabela.data.num_cols)
    df.to_csv("tabela.csv", index=False)

Níveis de hierarquia — e a distância até ao AKN4EU

Se procuras algo parecido com o AKN4EU — níveis explícitos, um dentro do outro — repara na linha nova da tabela acima: por omissão, todos os cabeçalhos do Docling ficam no mesmo nível. É por isso que não vias essa diferença no Markdown: capítulo e cláusula saem os dois como ##, sem distinção de profundidade. Não é um limite do formato — é uma opção desligada por omissão, chamada heading_hierarchy_options.

Verificado no código-fonte — o que essa opção faz, e o que não faz

Ligada (PdfPipelineOptions(heading_hierarchy_options=HeadingHierarchyOptions(enabled=True))), esta opção tenta atribuir um nível a cada cabeçalho, por esta ordem de confiança:

  1. Marcadores do PDF (um índice/sumário embutido) — as convenções do BTE não costumam ter.
  2. Numeração jurídica — mas o Docling reconhece as palavras-chave em inglês (chapter, article, section, clause…). "CAPÍTULO" e "Cláusula", em português, não são reconhecidos por esta via. Confirmei isto a ler o código-fonte, linha a linha — não é suposição.
  3. Estilo visual (tamanho de letra, negrito, maiúsculas) — esta via não depende de língua nenhuma. Se no PDF original "CAPÍTULO I" tem letra maior que "Cláusula 1.ª", esta via distingue os dois níveis correctamente. É o caminho mais promissor para as convenções.

E mesmo que isto funcione bem, o resultado é só um número — level=1, level=2 — não sabe que level=1 "é" um capítulo AKN4EU e level=2 "é" uma cláusula. Essa tradução continua a ser código teu, só que muito mais simples do que hoje: aplicas o teu RE_CLAUSULA ao título já isolado pelo Docling, em vez de o teres de encontrar primeiro dentro de um rio de texto. E confirmei também que o Docling não tem exportador nenhum para AKN4EU — os formatos de saída são Markdown, HTML, JSON, YAML, doctags e texto simples.

Sobre precisares de um "linting" a seguir

Sim — e isso não é sinal de o Docling estar mal, é o comportamento esperado de qualquer extractor por modelo. Confirmaste tu mesmo: as tabelas saem muito bem, a estrutura preserva-se em grande parte, mas alguns pormenores escapam. A resposta correcta não é "arranjar um Docling mais preciso" — é o que o AppCCT já faz hoje: uma camada de validação a seguir à extração, que confirma invariantes conhecidos (numeração de cláusulas sem saltos, capítulos em sequência de romanos, contagem de caracteres sem perdas). Olha para docs/validacao/ no repositório — é literalmente essa camada, já construída para o extractor actual; trocar de extractor não elimina essa necessidade, e o teu vocabulário para a construir é o mesmo (post-it, morada) mais o amostra de referência humana que já tens.
